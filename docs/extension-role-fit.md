## Workflow and data

Capture, correct, resolve warnings and save a current review. Select the resume intended for the application. Optional preferences are saved as the exact explicit context `{ "notes": "..." }`; profile fields and tracker preferences are not fetched or inferred. Blank preferences become null and require UNKNOWN alignment with empty notes. Assess the selected resume, or explicitly compare available resumes. Comparison results remain local and only the intended variant's matching result is attached.

The provider receives the final projected posting, complete selected resume text and optional preferences, under `role-fit-v1`. Experience definitions are STRONG (already has most required experience), POSSIBLE (qualified through transferable skills), and WEAK (lacks several important requirements). The prompt requires evidence, separates preference alignment, forbids invented qualifications and salary currency/period assumptions, and treats supplied text as untrusted data. Strict output validation rejects extra fields, missing fields, invalid ratings, oversized reports, malformed JSON and incomplete provider output. This validates structure; it cannot prove the model's factual reasoning. Review the result before delivery.

Full role-fit inputs do not reuse form-answer truncation. The pilot rejects complete message inputs above 120,000 UTF-16 units or 200,000 UTF-8 bytes before queuing. Preferences are bounded to 12,000 units. These are conservative extension budgets, not a claim about any provider's context capacity. A provider may reject smaller inputs; nothing is silently sliced. Use a suitable shorter evidence document or retain the capture Unassessed. Existing tracker assessment limits and the overall capture-v1 budget still apply.

Resume IDs identify the existing persistent slots (`resume-slot-1` through `resume-slot-3`). Replacing a slot keeps its ID; exact UTF-8 text hashes distinguish revisions. Posting hashes cover the final transport posting after salary and user-channel projection. Explicit preferences use canonical JSON hashes; absence stays null. Canonical JSON recursively sorts keys, preserves array order and hashes compact UTF-8. Local bindings also include capture/review, resume ID/label, gateway origin/configuration, model and prompt version. Local review hashing now uses canonical JSON too, because Chrome storage can reorder keys. Earlier captures with old review hashes need a fresh review; their immutable sources are not rewritten.

Jobs and results live under `fit-job:` independently from the `capture-delivery:` outbox. Jobs retain full input snapshots locally but no gateway key. A cross-page Web Lock allows one AI request at a time, including the existing form AI flows. Queued jobs recheck bindings before and after each request. Changed inputs become stale. A failed new attempt leaves matching successes intact. Reopening marks interrupted requests for explicit resumption; the previous request may already have reached the provider. Nothing promises work while the panel/browser is closed. No automatic AI retry occurs. A valid capture can be prepared Unassessed after failure.

Preparation attaches only a successful matching result and requires resolved current review. The transport contains `request_assessment:false` and the agreed extension assessment envelope; it never includes resume text, other variants, profile, gateway key, explicit preference text or complete prompts. Report text itself is evidence-based and can naturally mention experience. The exact compact body, including the report, must fit 262,144 UTF-8 bytes. Local sources and pilot exports survive every preparation or delivery error. Ordinary capture deletion removes its associated local jobs/outbox; Delete all local data also removes preferences and the separate tracker credential.

## Local delivery and recovery

Use a credential issued by the isolated local tracker's My preferences → Job Hunt extension. It is separate from the AI key. Connection negotiation verifies account, schema/capabilities and limits. Frozen deliveries bind account and origin, persist the complete request, hash it, and preserve its UUID, timestamps, report and bytes on retry. Changed current inputs pause delivery; no silent replacement UUID is generated. Disconnect, expiry, account or origin changes pause pending deliveries. Each explicit send verifies connection/access before capture delivery; there is no idle polling.

An uncertain response uses at most three receipt lookups and five POST attempts, with manual continuation and bounded exponential backoff. Retry-After is honored, including a longer server delay. A found receipt prevents a second POST. 401/403 pause for reconnect/access, 409 stops for inspection, 410 stops recreation of a deleted opening, 413 preserves the full local capture, and 422 shows validation details without blind retry. 429/503 wait until the recorded deadline. Retrying delivery never imports or calls the AI queue.

`applied` means the supplied fit was applied to a new lead. `stored_only` means capture history retained the fit while the existing opening's rating, status, priority and edits stayed intact. The UI distinguishes these outcomes. `assessment.state:"disabled"` describes server assessment execution and is not treated as failure of the supplied result.

## Verification and remaining interoperability limits

`npm test` exercises exact selected text and canonical hashes, final salary/channel projection, changed variants/preferences/model/gateway, stale review, full input transmission and explicit budget rejection, strict/malformed/partial reports, provider failure, matching success retention, serialized calls, queue restart, changed queued/in-flight inputs, attachment privacy, total UTF-8 bytes, account isolation, frozen retries, receipt recovery, HTTP error transitions and size/tamper rejection. Existing extraction/transport unit checks remain included.

`npm run test:tracker` compiles the actual sibling tracker routes with that repository's TypeScript dependency, substitutes only isolated storage/session dependencies, and serves them over ephemeral loopback HTTP. It verifies real authentication, accepted serializer hashes, applied/stored_only persistence, preserved manual edits, lost-response recovery, idempotent replay, cross-account isolation and stale-hash rejection. No production database client is loaded and no server resume/preferences/role-fit endpoint is called.

`npm run test:role-fit` checks the built installed extension with mocked gateway responses and the same actual local tracker harness: full selected resume, switching variants, malformed/provider failures, reopen, review/preferences invalidation, explicit comparison, private exports, production-origin rejection, local frozen delivery without another AI call, narrow layout and full reset. Existing capture and form browser suites check the original workflows separately. Tests use synthetic resume evidence and disposable browser profiles/databases.

Executed successfully on 2026-10-18: `npm run build`; `npm test` (48 passed, zero failed/skipped); `npm run test:tracker`; `npm run test:role-fit`; `npm run test:capture`; `npm run test:browser`; `npm run test:fill`; `npm run test:dropdowns`. The gateway was mocked, the tracker used disposable local JSON storage, and no production migration, upload or paid-provider request was performed.

No payload-field or state-transition contradiction has been found in accepted actual-route requests. Remaining limitations:

- `/api/v1/connection` does not expose the credential's authoritative expiration. The extension uses a conservative upper bound of 24 hours from first successful connection, preserves that bound when the same credential is reverified, and treats server 401 as authoritative. A token issued earlier can expire before the displayed local bound. Returning `expires_at` would allow an exact expiry display and earlier pause.
- Resume contents are intentionally excluded from the import. The tracker can validate supplied digest shapes and the posting hash, but cannot independently reconstruct the selected resume or preference context. These remain extension provenance rather than server-verified evidence.
- The local interop harness exercises actual routes with the tracker JSON storage adapter. It does not certify production deployment, migrations, PostgreSQL/Neon performance or production CORS/proxy behavior. Production enablement needs that separate verification and removal of the explicit loopback guard through a reviewed change.
- The configured real provider was not called. Mocked output tests verify orchestration and validation, not model quality or provider context capacity.

This change moves AI orchestration and its queue out of Job Hunt's server. Inference still runs at the configured provider. Posting/result storage, evidence transfer, credential checks and imports still require server/database work. Neon free-tier eligibility must be decided from measured usage after deployment; this pilot does not establish savings or guarantee a downgrade.
