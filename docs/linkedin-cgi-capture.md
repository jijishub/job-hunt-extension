# LinkedIn and CGI capture evidence

Implemented and inspected on 2026-10-18. This extends the existing capture/review/role-fit pilot. Production tracker restrictions, immutable captures, local exports, selected-resume bindings and frozen delivery are unchanged. No tracker schema or state-transition change is required.

## Root causes observed

The supplied [LinkedIn posting](https://www.linkedin.com/jobs/view/4386923096/) has its public description in `.description__text .show-more-less-html__markup`. The earlier extractor recognized neither selector and the page supplied no JobPosting JSON-LD in the inspected browser DOM. The original extractor returned zero candidates even though the duties and qualifications were present. An unrelated iframe generated a separate warning; it did not explain the missing description.

The supplied [CGI posting](https://cgi.njoyn.com/corp/xweb/xweb.asp?CLID=21001&page=jobdetails&JobID=J0326-1512&lang=1) exposes a 299-character opening paragraph in JSON-LD. Its full position description, duties, required/preferred qualifications, skills and employer statement are in `.job-desc .job-posting-content`, inside `form1`. The earlier extractor did not recognize that region and therefore returned only the structured excerpt. Reading the entire form would expose application controls; the adapter instead reads only the posting body, plus explicitly labelled posting header facts.

Excluded advertising/premium text cannot make a stale description appear fresh. The installed extension also rechecks title, description and selection identity before saving. Only a recognized, visible description expansion **button** is eligible for a click, at most once per capture. Links, Apply, employer navigation, consent and application controls are excluded. Extracted DOM text includes all available headings and list boundaries; existing source-size limits still warn explicitly rather than claiming completeness. Frames outside these adapters' scoped posting region are not treated as missing requirements.

## Review flow

The preview separates informational unknowns from review warnings. Missing work model/employment type do not block assessment and require no correction. Every original warning remains visible with its current status. The readiness box lists exactly the current blocking codes, affected fields and a concrete next action; transport errors such as stale review or excessive bytes also appear there.

After checking the intended job's title/employer/location and comparing the full posting and both preserved sources, check the identity/completeness confirmation and click **Confirm requirements and save review**. This records the layout/completeness explanation and current content-bound review. It uses existing v1 resolution actions: `verified_irrelevant` for the now-verified `requirements_unverified`, `structured_only` and `unverified_layout` warnings, and `use_rendered`, `use_structured` or `corrected` for the explicitly confirmed current description. The user is confirming the intended job and that the current description and qualifications contain all requirements; no sources or historical warnings are deleted.

Actual-route testing exposed a tracker rule that only `greenhouse-dom` and `lever-dom` are prevalidated. An otherwise reviewed CGI request initially returned 422 with reason `unverified_layout`. Both new adapters now emit that original warning, require the explicit identity/layout check above, and retain its resolution in transport. Client readiness also mirrors the server rule when a new-adapter capture lacks the warning. No adapter was silently added to the tracker's trusted list. Future prevalidation requires agreement with the tracker; the existing v1 resolution is sufficient for current explicit review.

Other conflicting fields, clipped/missing/truncated text and salary problems are not silently dismissed by this action. They retain their specific resolution controls and appear as remaining blockers. For the sample CGI page, confirming the full rendered description leaves the location conflict visible until the user saves an explained location decision. Corrections still invalidate resolutions/review, current fit and prepared requests. Existing manual correction and detailed resolution controls remain available.
